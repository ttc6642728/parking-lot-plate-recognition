# 车牌识别与停车场管理系统 · 系统介绍

## 一、系统概述

### 1.1 一句话定位

本系统是一个**离线可运行的车牌识别 + 停车场业务管理桌面应用**：用摄像头或图片识别车牌，
据此完成车辆入场、车位分配、出场计费、记录查询与营收统计，并以管理员 / 操作员两级权限
控制功能可见性。

它不是一个"识别算法的演示程序"，而是一个**业务流程闭环**：识别结果必须能落库、能计费、
能查询、能统计，每一环都有对应的界面与数据表。

### 1.2 基本信息

| 项目 | 内容 |
|---|---|
| 系统名称 | 车牌识别与停车场管理系统 |
| 系统形态 | Windows 桌面应用（PyQt5），单机部署 |
| 代码规模 | 约 9,100 行 Python（含测试与脚本） |
| 功能页面 | 登录页 + 7 个业务页 |
| 数据表 | 5 张（users / parking_lot / parking_records / members / blacklist） |
| 自动化测试 | 79 项通过、1 项条件跳过 |
| 外部依赖 | 仅 Python 包；模型文件随项目提供，**运行期无需联网** |
| 识别方案 | 深度学习（HyperLPR3）+ 传统 CV 双引擎，带置信度仲裁 |

### 1.3 它解决了什么问题

传统人工收费停车场有三个痛点：出入口通行慢、收费靠人算容易出错、数据留不下来。
本系统的应对方式分别是：

| 痛点 | 系统做法 |
|---|---|
| 通行慢 | 车牌自动识别，结果自动回填，人工只需确认 |
| 收费易错 | 计费规则代码化（车型 × 时长 × 会员折扣），单价集中在 `config.py` |
| 数据留存难 | 全量入库 SQLite，支持条件检索、Excel/CSV 导出、按日统计 |

同时补上了真实停车场必备的两个业务约束：**黑名单拦截**与**会员折扣**。

## 二、设计目标

按"能不能用、好不好用、靠不靠谱"三层拆解：

**功能层**

1. 车牌自动识别，支持图片与摄像头两种输入；
2. 入场自动分配车位，出场按规则自动计费；
3. 停车记录可查、可筛、可导出、可删改；
4. 会员管理与黑名单预警；
5. 车流与营收可视化。

**体验层**

6. 界面统一、信息分层清晰，关键结果（车牌、金额）一眼可见；
7. 识别失败要有明确提示，不能"静默出错"。

**质量层**

8. 业务逻辑有自动化测试覆盖，改代码不靠手工点；
9. 缺少可选组件（Tesseract、YOLO 权重、ONNX 模型）时能自动降级，不崩；
10. 密码不存明文，权限在界面与业务两层都生效。

## 三、总体架构

### 3.1 分层结构

系统严格分为三层，**上层只调用下层的方法，不跨层写 SQL**：

```
┌──────────────────────────────────────────────────────────────┐
│  表示层  ui/                                                  │
│                                                              │
│   LoginWindow ──→ MainWindow（侧栏导航 + 顶部信息条 + 内容栈） │
│                        │                                      │
│      ┌────────┬────────┼────────┬────────┬────────┬────────┐ │
│   车牌识别  入场登记  出场结算  停车记录  会员管理  黑名单  统计 │
│                                                              │
│   theme.py（设计令牌 + 全局 QSS）                              │
│   components.py（卡片 / 指标卡 / 车牌号牌 / 状态徽章 / 按钮）   │
│   icons.py（QPainter 现画的矢量图标，零资源文件依赖）           │
└───────────────────────────┬──────────────────────────────────┘
                            │ 调用业务方法，拿 dict，不碰 sqlite3
┌───────────────────────────▼──────────────────────────────────┐
│  业务层  core/ + auth/                                        │
│                                                              │
│   PlateRecognizer   双引擎识别 + 仲裁 + 置信度门槛             │
│   ParkingLotManager 车位分配、满位拦截、占用数增减             │
│   compute_fee()     车型 × 时长 × 会员折扣                    │
│   AuthManager       登录校验、PBKDF2 哈希、角色判定            │
│   Camera            摄像头采集（QTimer 驱动，1 fps 识别）      │
│   BlacklistChecker  入场前黑名单检查                          │
└───────────────────────────┬──────────────────────────────────┘
                            │ DAO 统一出口把 Row 转 dict
┌───────────────────────────▼──────────────────────────────────┐
│  数据层  db/                                                  │
│                                                              │
│   UserDAO  ParkingRecordDAO  MemberDAO  BlacklistDAO          │
│   ParkingLotDAO  ·  init_db.sql  ·  db/parking.db            │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 为什么这样分层

| 决策 | 原因 |
|---|---|
| 业务逻辑不写在 Widget 里 | 计费、车位规则要能被 pytest 直接调用，不必启动 GUI |
| DAO 出口统一返回 `dict` | `sqlite3.Row` 不支持 `.get()`，界面层一旦用它就会在"有数据"时崩 |
| 配置集中在 `config.py` | 单价、车位数、车位前缀、识别阈值都改一处生效 |
| `PlateRecognizer.shared()` 单例 | 模型加载要 2~3 秒、占约 200 MB，三个页面各建一个就是三份 |

### 3.3 一次完整业务的数据流

以"车辆入场"为例，串起三层：

```
用户点「选择图片」
   → recognize_widget 读取图像（cv2.imdecode，兼容中文路径）
   → PlateRecognizer.recognize(img)
        ├─ 线程 A：HyperLPR3 端到端识别
        ├─ 线程 B：内置管线定位 + 模板匹配
        └─ 仲裁 → RecognitionResult(车牌, 引擎, 置信度, 耗时)
   → 车牌回填到输入框（用户可改）
   → 点「确认入场」
   → EntryWidget 校验格式 → 查黑名单 → 查会员 → ParkingLotManager.allocate_spot()
   → ParkingRecordDAO.insert(...) → ParkingLotDAO.inc_used(+1)
   → 界面刷新剩余车位
```

## 四、技术选型

| 层次 | 选型 | 关键理由 |
|---|---|---|
| 语言 | Python 3.8+ | CV / GUI / 数据科学生态齐全，课程设计上手快 |
| GUI | PyQt5 | 跨平台；信号槽适合把识别线程与界面解耦；自带表格、堆栈容器 |
| 视觉 | OpenCV 4.x | 预处理、传统定位、摄像头采集的事实标准 |
| 识别（深度） | HyperLPR3 + onnxruntime | 中文车牌专用：检测四点 → 透视矫正 → CNN+BiLSTM+CTC 整串输出，不依赖字符切分 |
| 识别（传统） | 自研模板匹配 OCR | 零外部依赖，可在无 ONNX 环境兜底，标准车牌特写图上表现稳定 |
| 车辆检测 | ultralytics YOLOv8 | 仅用于"先找车、再在框内找牌"的粗定位 |
| OCR（可选） | Tesseract | 作为补充引擎；实测在本场景反而最弱，仅保留兜底 |
| 数据库 | SQLite3 | Python 内置、零部署、单文件便于打包与答辩演示 |
| 图表 | matplotlib | 与 Qt 集成简单（FigureCanvasQTAgg），柱状/折线足够 |
| 报表 | pandas + openpyxl | 一行导出 Excel / CSV，CSV 用 `utf-8-sig` 避免 Excel 乱码 |
| 测试 | pytest | 参数化方便，输出可读 |

**几个刻意的"不选"：**

- **不用 Web 框架**：课程设计强调桌面端与本地运行，SQLite + Qt 单机零配置，答辩现场不依赖网络。
- **不用图标字体 / png 图标**：图标全部用 `QPainter` 现画（`ui/icons.py`）。项目拷到别人电脑上若缺字形，
  字体图标会变成方块，而矢量绘制不会。
- **不引入 UI 框架**（如 qfluentwidgets）：QSS 足够表达设计意图，且避免额外依赖与版本冲突。

> 选型的取舍细节见 [`技术选型.md`](./技术选型.md)。

### 5.1 登录与权限

- 账号密码校验，密码以 **PBKDF2-SHA256 加盐哈希**存储（格式 `pbkdf2_sha256$迭代$salt$hash`），
  数据库中看不到明文；早期明文账号在首次登录成功后自动升级为哈希。
- 登录失败**不弹窗**，在表单下方显示内联错误条——弹窗需要多点一次"确定"，是打断式交互。
- 两级角色：`admin` 可访问全部功能；`operator` 的导航项「停车记录 / 会员管理 / 黑名单」置灰且不可点击。
  权限不只在界面置灰，`AuthManager.require_admin()` 在业务层同样校验。

默认账号（首次启动自动创建）：

| 账号 | 密码 | 角色 |
|---|---|---|
| admin | admin123 | 管理员 |
| operator | 123456 | 操作员 |

### 5.2 车牌识别

系统的核心模块，详见第六章。界面能力：

- **图片识别**：文件对话框选图 → 识别 → 结果回填，画布显示带标注的图；
- **摄像头识别**：后台线程采集（约 30 fps），每 1 秒提交一次识别；
  识别到的车牌位置在实时画面上框出，结果同步到右侧面板；
- **打开不卡界面**：采集与识别都在工作线程执行，点按钮立即返回，
  状态栏先显示"正在打开…"，收到第一帧才切换为"采集中"；
- **失败有明确原因**：区分"没找到设备"与"能打开但取不到画面（被其他程序占用）"，
  并自动探测本机可用设备号；
- **结果面板**：仿车牌的蓝色号牌块（视觉焦点）、置信度进度条、实际生效引擎、耗时；
- **分歧提示**：两引擎结果不一致时，状态栏显示「引擎结果有分歧」，鼠标悬停看完整明细；
- **历史列表**：保留本次会话的识别记录（车牌 · 引擎 · 置信度）。

### 5.3 入场登记

- 车牌可自动识别回填，也可手动输入；
- 格式软校验：不符合规则时弹确认框而非直接拒绝（避免演示时因格式细节卡住流程）；
- **黑名单拦截**：命中黑名单弹窗预警；
- **会员识别**：命中 `members` 且在有效期内则标记为会员；
- **车位分配**：从 `A001` 起找第一个未被占用（未出场）的车位号；
- **满位拦截**：`ParkingLotManager.is_full()` 为真时提示"停车场已满，禁止入场"；
- 写入 `parking_records`，`parking_lot.used_spots + 1`。

### 5.4 出场结算

- 按车牌查最近一条**未结算**记录；
- 计费规则：

  | 项目 | 规则 |
  |---|---|
  | 小型车 | 2 元 / 小时 |
  | 大型车 | 4 元 / 小时 |
  | 计时 | 不足 1 小时按 1 小时；超 1 小时零 1 秒按 2 小时（向上取整） |
  | 会员 | 乘 `members.discount`；字段缺失时回退 `config.MEMBER_DISCOUNT` |

- 回写出场时间、时长（秒）、费用；`used_spots - 1` 释放车位；
- 右侧做成"结算单"样式：入场时间、停车时长、车位号、会员标记、**应收金额（26px 大字）**。

### 5.5 停车记录

- 表格展示全部记录，11 列（ID / 车牌 / 类型 / 车位 / 入场时间 / 出场时间 / 时长 / 费用 / 会员 / 操作员 / 备注）；
- 筛选：车牌模糊查询、入场时间段、仅看在场的；
- 备注列吸收剩余宽度，其余按内容自适应——**宁可横向滚动，也不把时间截成 `2026-10-10 13…`**；
- 空结果时表格上覆盖"没有符合条件的记录"，而不是一片空白；
- 导出 Excel / CSV；
- 删除单条记录：若删除的是在场未结算记录，**同步释放车位**（否则车位会永久泄漏）。

### 5.6 会员管理

- 录入车牌、姓名、电话、有效期、折扣；
- 支持修改、删除、续期；
- 入场时自动判定会员身份，出场时按该会员的折扣结算；
- 会员表的日期与电话列按内容撑开，避免被截断。

### 5.7 黑名单

- 新增 / 删除黑名单条目，记录加入原因与时间；
- 车辆入场时实时检查，命中即弹窗预警；
- 黑名单车辆不阻止入场流程，只做提示——真实停车场需要人工判断（如误报、临时放行）。

### 5.8 数据统计

- 4 张指标卡：总车位数、在场车辆、今日车流、今日营收；
- 趋势图：车流（柱状）+ 营收（折线）双轴；
- 默认区间为最近 7 天（30 天视图里新系统大半是空柱子，反而看不出趋势）；
- **按日历补齐空缺日**：`daily_stats` 只返回有记录的天，若不补，10-11 与 10-13 会被画成相邻两天，
  趋势图会"骗人"。补 0 后横轴才是真实时间序列；
- 一键导出 Excel / CSV。

> 逐模块的实现细节见 [`功能模块说明.md`](./功能模块说明.md)。

## 六、核心设计：双引擎识别与置信度仲裁

这是本项目投入最多、也最能体现设计思考的部分。

### 6.1 问题起点

所有合成测试图都能识别，但换成一张**清晰、正面、光照均匀的真实车牌照片**（冀T15888），
输出却是 `津T1111`、`渝T11HH4`、`甘H1HMDN` 这类乱码，且每次不同。

图像质量没有问题，所以问题在算法本身。把流程拆成"定位 → 二值化 → 切分 → 匹配"四步逐段验证：

| 环节 | 诊断结论 |
|---|---|
| 二值化 | **正常**。车牌区域二值化后七个字符清晰可辨，无粘连断裂 |
| 切分 | **错误**。原实现假设"7 位字符等距"，直接 7 等分 |
| 匹配 | **错误**。每个单字符都匹配错，相似度仅 0.33~0.43 |
| 拒识 | **缺失**。错误结果只要格式合法就当成"识别成功"返回 |

**切分错在哪**：省份汉字宽度约为字母的 1.5 倍，第 2、3 位之间还有一个分隔圆点，
7 等分网格整体错位半个字符，每格切出来都是"半字符 + 半字符"：

```
|冀 |T·|1 |58|8 |8 |   ← 7 等分（全部错位）
|冀 |T |·|1 |5 |8 |8 |8 ← 投影切分（正确）
```

**匹配错在哪**：中国车牌用国标 GA36 专用字体（长黑体），与系统黑体的笔画粗细、
字宽比例、转角处理都不同。模板匹配的前提是"输入字体与模板字体同源"，
这个前提在真实车牌上不成立，相似度天然只有 0.3~0.4。**这是路线天花板，调参救不回来。**

**最危险的是第三点**：`津T1111` 格式完全合法，置信度只有 0.29，却一路畅通进入业务流程。
**进错车、收错费，比识别失败严重得多。**

### 6.2 方案：不换引擎，让两个引擎互相兜底

| 引擎 | 原理 | 擅长 | 会错的地方 |
|---|---|---|---|
| HyperLPR3 | YOLO 检四点 → 透视矫正 → CNN+BiLSTM+CTC 输出整串 | 真实抓拍：倾斜、光照不均、有车身上下文 | 纯车牌特写合成图（训练分布不同） |
| 内置管线 | 定位 → 二值化 → 切分 → 字体模板匹配 | 标准车牌特写、完全离线 | 真实车牌（字体不同源） |

两者失效的条件**恰好互补**，所以不是二选一替换，而是都跑一遍再仲裁。

### 6.3 仲裁规则

关键判断：**不看"谁置信度高"**。两个引擎的置信度含义不同（一个是 CTC 序列概率，
一个是模板相似度），不可直接比较。

真正可靠的信号是**内置管线对自己结果有多确信**：

| 内置自评相似度 | 物理含义 | 处置 |
|---|---|---|
| ≥ 0.55 | 输入字体与模板同源（程序渲染的标准图） | 采信内置结果 |
| < 0.55 | 模板匹配不上真实字形（真实车牌） | 采信 HyperLPR3 |

这个信号恰好对应"字体是否同源"，可解释性强，也正好卡在两个引擎的失效边界上。

完整决策共 6 个分支：

```
两引擎都无结果 ────────────────→ 报"未检测到车牌"
仅深度引擎有结果 ──────────────→ 用深度结果
仅内置管线有结果 ──────────────→ 用内置结果
两者结果一致 ──────────────────→ 标记「双引擎一致」，取深度引擎的框
两者不一致，内置自评 ≥ 0.55 ───→ 用内置
两者不一致，内置自评 < 0.55 ───→ 用深度
```

此外还有一道**置信度门槛**：深度结果低于 `PLATE_MIN_CONFIDENCE = 0.70` 直接丢弃，
不参与决策；两引擎都不达标时如实报识别失败，而不是硬给一个结果。

### 6.4 并行执行

两个引擎用 `ThreadPoolExecutor(max_workers=2)` 并行，总耗时取较慢的那个而非相加。
onnxruntime 与 OpenCV 推理时都会释放 GIL，双线程确有收益（实测 1.4 s → 0.7 s）。
任一引擎抛异常不影响另一个，异常时回退串行，保证功能不中断。

### 6.5 量化结果

复现命令：`python eval_recognition.py --augment`

| 测试集 | 内置管线 | 双引擎 |
|---|---|---|
| 基础集（1 张真实 + 6 张合成） | 6/7（86%） | **7/7（100%）** |
| 真实照片的 17 种退化增强<br>（旋转 ±12°、亮度 0.55~1.35、模糊 13×13、缩放至 20%、噪声、组合退化） | 0/17（0%） | **17/17（100%）** |

继续加大强度仍可识别：旋转 ±15°、缩小到 18%（车牌约 200 px 宽）、模糊 17×17、亮度 ×0.2。
真正会失败的场景是**车牌被遮挡、严重运动模糊、极端逆光过曝**——这类输入人也看不清。

### 6.6 一个隐蔽的工程坑：DLL 加载顺序

改进过程中最耗时的问题不是算法，而是：

```
DLL load failed while importing onnxruntime_pybind11_state: 动态链接库(DLL)初始化例程失败
```

现象极具误导性：**单独跑识别脚本正常，一进 GUI 就失败**，日志里只有一行"降级到内置管线"，
表现为"识别率突然变差"，很容易误判成模型损坏或偶发问题。

最小复现后发现规律只取决于导入顺序：

| 导入顺序 | 结果 |
|---|---|
| 先 `import onnxruntime`，再 `import PyQt5` | ✅ 正常 |
| 先 `import PyQt5`，再 `import onnxruntime` | ❌ DLL 初始化例程失败 |

`os.add_dll_directory()` 无效，说明不是"找不到 DLL"，而是两个库的 CRT / 全局初始化冲突。
处理方式是在 `main.py`、`tests/conftest.py` 顶部**强制先加载 onnxruntime**（代码里有注释说明，
不要调换顺序），并在 `core/lpr_engine.py` 中识别这个特定错误、追加排查提示。

> 完整诊断过程见 [`识别准确率报告.md`](./识别准确率报告.md)。
