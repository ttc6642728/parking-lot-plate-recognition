# 车牌识别准确率改进报告

> 记录"真实车牌识别率不足"问题的定位过程、改进方案与量化验证结果。
> 所有数据均可用 `python eval_recognition.py --augment` 复现。

---

## 一、问题现象

合成测试图 6/6 全对，但换成真实照片后识别结果完全不靠谱：

| 输入 | 真值 | 改进前识别结果 |
|---|---|---|
| 真实照片（奥迪 A8L 车尾，清晰正面） | 冀T15888 | `津T1111` / `渝T11HH4` / `甘H1HMDN`（每次不同） |

注意这张图的质量并不差：光照均匀、车牌正对镜头、字符边缘锐利、无遮挡。
**在这种理想条件下都识别不出来，说明不是"图不好"，而是算法本身有结构性缺陷。**

---

## 二、逐环节定位

把流程拆成「定位 → 二值化 → 切分 → 匹配」四步，逐步打印中间结果：

### 2.1 二值化其实是好的

把车牌区域单独裁出来做二值化，效果相当干净，七个字符（冀 T · 1 5 8 8 8）
清晰可辨，没有任何粘连或断裂。

**结论：二值化不是问题。** 这一步没问题，就不该动它。

### 2.2 切分策略是错的（主因其一）

原实现假设车牌是"7 位字符、等距排列"，直接把字符区 7 等分。

但这个假设不成立：

- 省份汉字宽度约为字母的 **1.5 倍**；
- 第 2、3 位之间还有一个**分隔圆点**；
- 汉字高度通常略高于字母数字。

结果 7 等分网格整体错位半个字符，每格切出来的都是"半字符 + 半字符"的拼接：

```
|冀 |T·|1 |58|8 |8 |   ← 7 等分网格（全部错位）
```

改为按**垂直投影真实切分**后，切分位置完全正确（冀 | T | · | 1 | 5 | 8 | 8 | 8）。

### 2.3 字体模板匹配是错的（主因其二）

切分修好后，问题暴露得更清楚了：**每个单字符都匹配错误**。

| 真值 | 模板匹配结果 | 相似度 |
|---|---|---|
| 冀 | Y | 0.35 |
| T | T | 0.43 |
| 1 | S | 0.35 |
| 5 | 4 | 0.35 |
| 8 | 1 | 0.33 |
| 8 | 4 | 0.36 |

原因：中国车牌用的是 **GB GA36 专用字体**（长黑体），和 Windows 系统黑体在笔画粗细、
字宽比例、转角处理上都有明显差异。模板匹配依赖"输入字体与渲染字体同源"，
这个前提在真实车牌上根本不成立，相似度天然只有 0.3~0.4。

**这是模板匹配路线的天花板，靠调参救不回来。**

### 2.4 缺少拒识机制（放大器）

更麻烦的是：错误的字符拼起来如果恰好满足车牌格式，系统就当成"识别成功"返回。
`津T1111` 格式完全合法，置信度只有 0.29，却一路畅通无阻地进入了业务流程。

**进错车、收错费，比识别失败严重得多。**

## 三、改进方案

### 3.1 引入 HyperLPR3 作为真实场景主力

HyperLPR3 是面向中文车牌的端到端方案：

```
YOLO 检测车牌四点 → 透视矫正 → CNN + BiLSTM + CTC 直接输出整串字符
```

它不需要切分字符，也不需要字体模板，避开了上面两个坑。
模型文件（4 个 onnx，共 17.5 MB）已随项目放在 `models/hyperlpr3/`，离线可用。

### 3.2 保留内置管线，做"双引擎 + 置信度仲裁"

但 HyperLPR3 也有短板：它在真实车图上训练，遇到**纯车牌特写、没有车身上下文**
的合成图反而会错（实测把 `沪B5M2N9` 认成 `沪B5N2N9`、`川F2H6W8` 认成 `桂F2H6W8`）。

所以不是简单替换，而是让两个引擎都跑，再决定信谁。

**仲裁依据不看"谁置信度高"**（两者置信度含义不同，不可比较），
而是看**内置管线对自己结果有多确信**：

| 内置自评相似度 | 含义 | 处置 |
|---|---|---|
| ≥ 0.55 | 输入字体与模板同源（标准渲染图） | 采信内置 |
| < 0.55 | 模板匹配不上真实字形（真实车牌） | 采信 HyperLPR3 |

这个信号恰好反映了"字体是否同源"，比拍脑袋定阈值可靠，也方便答辩解释。
两引擎结果一致时标记「双引擎一致」，给用户更强的可信度提示。

### 3.3 修掉内置管线自身的三个缺陷

即使只作为兜底，内置管线的问题也该修：

| 问题 | 原实现 | 改为 |
|---|---|---|
| 裁边吃字符 | 按 7% 固定比例裁，把最外侧字符裁掉一半 | 按投影识别"横贯整幅"的边框行列，只裁真正的边框 |
| 等分错位 | 无条件 7 等分 | 投影切分与等分网格两种策略择优 |
| 圆点干扰 | 分隔圆点被当成字符参与匹配 | 按宽高比 < 0.22 剔除 |

注意保留等分策略是必要的：合成图是严格等距排版的，投影反而容易被笔画断开而过分割，
**两种策略各有胜出场景**，实测择优后在 6 张合成图上恢复 6/6。

### 3.4 置信度门槛与分歧提示

- 低于 `PLATE_MIN_CONFIDENCE`（0.70）的深度结果直接丢弃，不参与决策；
- 两引擎结果不一致时，`RecognitionResult.note` 记录完整分歧信息；
- UI 状态栏显示「⚠ 引擎结果有分歧」，鼠标悬停可看明细，提示人工确认。

| 类别 | 强度 | 内置管线 | 双引擎 |
|---|---|---|---|

内置管线在退化样本上交白卷并不意外——它连清晰原图都认不出，
退化只是让错误"更明显"而已。

### 4.3 能力边界（额外测试）

继续加大退化强度，观察失效点：

| 测试 | 结果 |
|---|---|
| 旋转 ±15° | ✓ |
| 缩放到 18%（车牌仅约 200px 宽） | ✓ |
| 高斯模糊 17×17 | ✓ |
| 亮度 ×0.2（接近全黑） | ✓ |

在合理拍摄范围内未触及失效边界。真正会失败的场景是**车牌被遮挡、
严重运动模糊、极端逆光过曝**——这类输入人也看不清。

## 五、踩坑记录：PyQt5 与 onnxruntime 的 DLL 加载顺序

这是本次改进中最隐蔽的一个问题，值得单独记录。

### 现象

在 GUI 里调用识别时，HyperLPR3 始终不可用，日志只有一行：

```
HyperLPR3 初始化失败，将降级到内置管线：
ImportError: DLL load failed while importing onnxruntime_pybind11_state:
动态链接库(DLL)初始化例程失败。
```

但**单独跑识别脚本（不启动 GUI）却完全正常**，很容易误判成"偶发问题"或
"模型文件损坏"。

### 定位

用最小例子对比两种导入顺序：

| 顺序 | 结果 |
|---|---|
| 先 `import onnxruntime`，再 `import PyQt5` | ✅ 正常，能建 InferenceSession |
| 先 `import PyQt5`，再 `import onnxruntime` | ❌ DLL 初始化例程失败 |

进一步排除：
- `os.add_dll_directory(onnxruntime/capi)` 无效 → 不是"找不到 DLL"；
- 与是否在线程里无关，主线程同样失败；
- 换 `detect_level`、换模型文件都无效。

结论：这是两个库的 CRT / 全局初始化冲突，**只由加载顺序决定**。
"初始化例程失败"（`ERROR_DLL_INIT_FAILED`）通常意味着 DllMain 执行时
依赖的运行时状态已被另一版本占用。

### 处理

在导入 PyQt5 **之前**先加载 onnxruntime：

- `main.py` 顶部（注释说明了原因，不要调整顺序）；
- `tests/conftest.py` 顶部（否则相关用例会静默 skip）；
- 自己写脚本时同样要在 `from PyQt5...` 之前 `import onnxruntime`。

同时在 `core/lpr_engine.py` 里识别这个特定的错误信息，追加明确的排查提示，
避免以后再被当成"模型问题"排查半天。

> 为什么不用 `sitecustomize` / `.pth` 全局预加载？
> 那会污染用户环境，且对不走本项目的脚本产生副作用。
> 在入口处显式前置加载，影响面最小。

## 六、性能

| 指标 | 数值 |
|---|---|
| 单张识别（双引擎并行） | 约 0.6 ~ 1.3 s |
| 首次加载（含模型加载） | 约 2 ~ 3 s |
| 模型内存占用 | 约 200 MB |

双引擎**并行执行**而非串行，总耗时取较慢的那个而不是相加。
对"入场/出场单次识别"的场景完全够用；若将来要做视频流实时识别，
可改为固定使用 HyperLPR3 单引擎（约 200 ms/帧）。

## 七、遗留说明（答辩时建议主动交代）

1. **17/17 不等于"任意场景 100%"。** 退化增强是在同一张真实照片上做的，
   能证明抗干扰能力，不能证明对任意车型、任意车牌都同样准。
   要得到严谨结论，需要 CCPD 这类真实数据集做批量评测。

2. **仲裁规则来自实测归纳，不是理论推导。** 0.55 这个阈值是在"真实图 0.29、
   合成图 0.67~0.77"这组观测上定的，样本量有限。工程上够用，
   但更严谨的做法是收集更多样本后重新标定。

3. **HyperLPR3 是第三方开源项目**（Apache-2.0），本项目的贡献是
   双引擎集成、仲裁策略与内置管线的修复，而不是识别模型本身。
   这一点在答辩时应如实说明。
